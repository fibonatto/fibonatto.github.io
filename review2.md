# Technical Architecture Documentation: review2.md

## 1. Executive Summary & Taxonomy
The system is formally classified as a **Client-Side SPA Engine with Build-Time Materialization (Content-as-Binary)**. Unlike standard Static Site Generators (SSG) that produce multiple HTML files, this architecture compiles all site content into the WebAssembly binary's `.rodata` section at build-time. Execution is handled by a C-based runtime compiled to WASM, which performs zero-allocation parsing and DOM hydration via a minimal JavaScript Hardware Abstraction Layer (HAL).

## 2. Core Subsystems & Codebase Map

### Build-Time Pipeline
*   **Content Packing:** `tools/packer.c` scans the `contents/` directory, parses Markdown front-matter, and emits `generated/contents_data.h`. This file contains raw hex-encoded C-arrays (`post_data_<slug>`) and a binary-searchable index (`post_slug_index`).
*   **Asset Hashing & Optimization:** `build.sh` implements SHA256-based content hashing for static assets (e.g., `pfp.avif`, `app.wasm`). It utilizes `emcc` with `-Oz` (aggressive size optimization) and `-flto` (Link-Time Optimization) to minimize binary footprint.

### Memory & Execution Subsystem
*   **Runtime Entry:** `src/main.c` orchestrates the bootstrap sequence: theme restoration, graphics initialization, and initial routing.
*   **Global Buffer:** `src/buffer.c` / `include/buffer.h` define `g_html_buf`, a static 128KB `Buffer` structure. This serves as the primary accumulator for all HTML generation, eliminating the need for a runtime heap allocator.

### State & Routing Subsystem
*   **Routing Logic:** `src/router.c` manages application state transitions between `PAGE_HOME`, `PAGE_BLOG_INDEX`, and `PAGE_ARTICLE`. It uses `find_post_index_by_slug` (generated by the packer) to resolve routes in $O(\log n)$ time.

### Parsing & Transpilation Core
*   **Markdown Parser:** `src/markdown.c` implements a line-based state-machine parser using `struct str_view` (pointer + length). It supports headers, images, code blocks, and custom graph shortcodes without performing heap allocations.
*   **LaTeX Parser:** `src/math.c` is a recursive descent parser that transpiles LaTeX math syntax directly to MathML. It utilizes a `MathParser` state machine and a static `CMD_TABLE` for token mapping.

### UI Layout & Configuration
*   **Visual Constants:** `src/config.c` defines the Nord-based palette and static CSS strings injected into the DOM.
*   **Rendering:** `src/ui.c` and `src/pages.c` provide the high-level DSL for page construction (e.g., `add_paragraph`, `add_image`).

### Dead/Isolated Code
*   **`./heart.c`:** An isolated file at the root. Implementation reveals an intentional memory leak (malloc without free, followed by pointer nullification) and is not linked in `build.sh`.
*   **`config.plist`:** A Clang/LLVM diagnostics artifact (`plist` format) likely generated by a static analyzer or LSP, confirmed by the `clang_version` key.

## 3. The WASM/JS Boundary & FFI Architecture

### Exported Surface (WASM → JS)
Functions exposed via `EMSCRIPTEN_KEEPALIVE` in `src/router.c`, `src/ui.c`, and `src/markdown.c`:
*   `_main`: Entry point.
*   `_ui_toggle_theme`: Switches global theme state and updates the UI.
*   `_switch_page`: Direct page transition logic.
*   `_handle_route` / `_handle_current_route`: URL-to-state resolution hooks.
*   `_draw_frame`: Triggers the 2D Canvas redraw.

### Imported Capabilities (JS → WASM)
Implemented via `EM_JS` macros in `src/js_api.c`:
*   `sys_set_html`: Performs atomic DOM updates using `document.createRange().createContextualFragment()` and `el.replaceChildren()`.
*   `sys_load_theme` / `sys_save_theme`: Interface for `LocalStorage` persistence.
*   `init_graphics`: Sets up a high-DPI 2D Canvas for header rendering.

### Data Marshalling Protocol
*   **String Passing:** C-strings are passed to JS as pointers; the JS layer uses Emscripten's `UTF8ToString` to read from the WASM linear memory.
*   **Struct Introspection:** In `update_theme_colors`, the JS layer reads `struct theme` members by manually calculating offsets (e.g., `t + 4`, `t + 8`) and accessing the `HEAP32` typed array.

## 4. Memory Model & Lifecycle

### Allocation Policy
The runtime operates with a **zero-malloc footprint**. Post-bootstrap, all rendering operations utilize the static global `g_html_buf`. Content residency is strictly in the `.rodata` section of the WASM module.

### The Global Buffer Mechanics
`g_html_buf` is capped at **131,072 bytes** (`BUFFER_CAPACITY`). Every rendering cycle begins with `buf_reset`, which zeros the length but does not deallocate memory. Safety is enforced via the `overflow` boolean flag; if exceeded, `ui_end_render` displays a fallback error message instead of corrupting memory.

### Execution Lifecycle Flow
The synchronous execution path for every page load or route change:
1.  **Bootstrap:** `main()` initializes state and HAL hooks.
2.  **Router Hooking:** `sys_init_router` binds `popstate` and `hashchange` to WASM callbacks.
3.  **Global State Page Mutation:** The router updates `state.page`.
4.  **Buffer Reset:** `ui_begin_render` resets `g_html_buf`.
5.  **Parser Flush:** Markdown/Math parsers walk through `.rodata` content, appending HTML to `g_html_buf`.
6.  **Atomic DOM Hydration:** `ui_end_render` calls `sys_set_html`, replacing the `#feed` element's children in a single operation.

## 5. Performance-Oriented Design Decisions
*   **Fixed-Size Buffers:** Use of `BUFFER_CAPACITY` prevents allocation overhead and fragmentation.
*   **Zero-Allocation Tokenization:** The Markdown parser uses string views, avoiding `substring` or `malloc` during text processing.
*   **Compile-Time Content Packing:** Eliminates runtime I/O and network requests for articles.
*   **Optimization Flags:** `-Oz` for code size and `wasm-opt` for WASM-specific instruction tuning.
*   **Lazy Loading:** `sys_set_html` implements a custom `img-placeholder` system that converts placeholders to `Image` objects with `loading="lazy"` (or `fetchpriority="high"` for LCP).
