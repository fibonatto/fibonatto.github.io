Deployment and Upgrades

Deployment and Upgrades

0. Staff-level lens

Deployment is the moment a design becomes irreversible, and upgradeability is a deliberate hole in that irreversibility. Both are security and governance decisions as much as engineering tasks. At Staff and Principal scope you are expected to:

  • build deployment pipelines that are reproducible, reviewed, rehearsed, and verifiable, with keys and roles set up safely;
  • decide between immutable and upgradeable designs, and define the upgrade governance that makes the choice trustworthy;
  • understand proxy patterns and storage layout well enough to prevent corruption and to review upgrades;
  • plan migrations, rollbacks, and incident-driven upgrades before they are needed.

1. Deployment as a controlled release

A deployment pipeline for contracts should be as rigorous as for any critical production system, and more, because there is no rollback of state.

  • Reproducible builds: pinned compiler version, optimizer settings, EVM version, library versions (lock files or vendored submodules), and a build output that can be re-created bit for bit; record the metadata hash, which makes verification possible.
  • Scripted deployments: use scripts (Foundry scripts, Hardhat Ignition or deploy scripts) instead of manual steps; parameterize by network; keep the scripts reviewed and versioned; simulate on a fork first; produce a manifest of deployed addresses, constructor arguments, and transaction hashes.
  • Environments: local, testnet (check which testnets are currently maintained; they are retired periodically), staging on a fork or dedicated deployment, and mainnet; use the same scripts across them.
  • Deterministic deployment: CREATE2 (salt and init code hash) or CREATE3 factories give predictable addresses across chains, which simplifies multi-chain configuration; be aware that the init code and constructor arguments affect CREATE2 addresses and that CREATE3 decouples them.
  • Verification: publish verified source on block explorers (Etherscan-style and Sourcify, which matches by metadata) so anyone can read and check the code; verify proxies and implementations; keep flattened or standard-JSON inputs.
  • Role and ownership setup: after deployment, configure roles, transfer ownership from the deployer to the multisig or timelock, renounce unneeded deployer powers, set initial parameters and caps, and verify each step on-chain with a post-deployment script that fails if anything differs from the specification.
  • Post-deploy smoke tests: call view functions, check roles, simulate small transactions, and run the invariant checks against the live deployment on a fork of the final state.
  • Gating: deployment to mainnet requires a checklist (audits done, findings resolved, tests green, monitoring and alerts configured, runbooks ready, keys and signers confirmed, caps set, announcements prepared) and sign-off by named owners.
  • Key handling: deploy from hardware wallets or KMS-backed signers, not from environment-variable private keys; use throwaway deployer accounts with no residual privileges.
// script/Deploy.s.sol: Foundry deployment script (sketch).
// Run: forge script script/Deploy.s.sol --rpc-url $RPC_URL --account deployer --broadcast --verify
import {Script, console2} from "forge-std/Script.sol";
import {Vault} from "../src/Vault.sol";

contract Deploy is Script {
    function run() external returns (Vault vault) {
        vm.startBroadcast();            // signer comes from --account (keystore) or --ledger, not a plaintext key
        vault = new Vault();
        vm.stopBroadcast();
        console2.log("Vault deployed at", address(vault));
    }
}

2. Immutable versus upgradeable

Aspect Immutable contracts Upgradeable contracts
Trust Users trust only the code Users also trust whoever controls upgrades
Bug response Migrate to a new deployment; funds at risk until then Patch in place, possibly quickly
Composability Stable addresses and behavior for integrators Behavior can change under integrators
Complexity Simpler Proxy, storage layout, and initializer hazards
Governance burden Low Requires multisig, timelock, monitoring, processes
Regulatory and legal Fewer admin levers Admin control can bring obligations

Guidance: use immutability where the logic is small, stable, and heavily verified (token cores, simple primitives). Use upgradeability where requirements will evolve and the operator is accountable, but make upgrades slow, observable, and constrained. Mixed designs (an immutable core with upgradeable periphery or parameters in bounded registries) often work best. Treat "upgradeable" as a trust assumption and state it publicly.

3. Proxy patterns

  • Mechanism: a proxy contract holds state and delegates calls to an implementation contract via DELEGATECALL; upgrading changes the implementation address; storage stays in the proxy.
  • Transparent proxy: the proxy has an admin that can upgrade but cannot call the implementation; non-admins are forwarded; avoids selector clashes between the proxy admin functions and implementation functions.
  • UUPS (ERC-1822 with ERC-1967 slots): the upgrade logic lives in the implementation; the proxy is lighter (cheaper calls); the risk is that an implementation without upgrade logic (or with broken authorization) bricks upgradability or lets anyone upgrade.
  • Beacon proxies: many proxies read their implementation from a shared beacon; upgrading the beacon upgrades all instances at once; suited to factories of similar contracts.
  • Minimal proxies (EIP-1167 clones): cheap clones that delegate to a fixed implementation; not upgradeable by themselves.
  • Diamond (EIP-2535): a proxy routes selectors to multiple facets; flexible and large-contract friendly; complex to reason about and audit.
  • Non-proxy upgrade paths: deploy a new contract and migrate state and users (clean but disruptive); registries and routers that point to current modules; parameter-only upgradeability through bounded setters.
  • Standard storage slots: ERC-1967 defines slots for the implementation, admin, and beacon so that they cannot collide with ordinary variables.
  • Metamorphic contracts (CREATE2 plus SELFDESTRUCT) no longer work as before after the Cancun change to SELFDESTRUCT; do not rely on them.

4. Storage layout and initialization safety

  • Rules: in an upgradeable contract, never reorder, remove, or change the type of existing state variables; only append new ones; be careful with inheritance changes (the linearized order matters); keep storage gaps (the older convention) or, better, use namespaced storage (ERC-7201), which places each module's variables in a struct at a slot derived from a namespace hash, so modules cannot collide and ordering matters less. Recent OpenZeppelin upgradeable contracts use namespaced storage.
  • Initializers replace constructors: the proxy's storage is initialized by calling an initialize function once; protect it with initializer and reinitializer modifiers; call _disableInitializers() in the implementation's constructor so nobody can initialize the implementation directly; initialize every inherited module; never leave a proxy uninitialized between deployment and initialization (deploy and initialize atomically).
  • Constructors and immutables in the implementation affect only the implementation's code, not the proxy's storage: values set there are shared by all proxies; do not use constructor logic expecting per-proxy state.
  • DELEGATECALL hazards: an implementation that makes DELEGATECALL to attacker-controlled targets can be hijacked; an implementation that can self-destruct (before Cancun) could be destroyed; function selector collisions between proxy and implementation functions.
  • Tooling: upgrade plugins validate storage layout compatibility and detect unsafe patterns; run them in CI and before every upgrade; add tests that perform the upgrade on a fork and compare state before and after.
// UUPS upgradeable contract (OpenZeppelin v5 style sketch).
import {Initializable} from "@openzeppelin/contracts-upgradeable/proxy/utils/Initializable.sol";
import {UUPSUpgradeable} from "@openzeppelin/contracts-upgradeable/proxy/utils/UUPSUpgradeable.sol";
import {OwnableUpgradeable} from "@openzeppelin/contracts-upgradeable/access/OwnableUpgradeable.sol";

contract VaultV1 is Initializable, OwnableUpgradeable, UUPSUpgradeable {
    uint256 public fee;

    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() { _disableInitializers(); }

    function initialize(address owner_, uint256 fee_) public initializer {
        __Ownable_init(owner_);
        fee = fee_;
    }

    // Upgrade authorization: in production, restrict to a timelock controlled by a multisig.
    function _authorizeUpgrade(address newImplementation) internal override onlyOwner {}
}

5. Governing upgrades

  • Who can upgrade: ideally a timelock whose proposer is a multisig or governance contract; never a single EOA.
  • Delay: a public delay (commonly at least two days for serious protocols; longer where users need exit time) between announcing and executing an upgrade, so users can exit and monitors can review.
  • Transparency: publish the new implementation address, source, diff, audit report, and migration steps before the delay ends; verify the code on explorers; provide a simulation of the upgrade transaction.
  • Emergency paths: a narrowly scoped pause (and unpause) role for incidents, held by a guardian set with fast response; avoid giving emergency roles the ability to upgrade arbitrarily; decide who may bypass the delay and under what conditions, and publish that policy.
  • Review of upgrades: treat each upgrade as a new release: diff review, storage layout check, tests on a fork with migrated state, audit of the changes, and a rollout plan.
  • Rollback: you cannot undo state changes, but you can upgrade back to the previous implementation if storage remains compatible; plan for data migrations that are reversible, and test the rollback path.
  • Scoping upgrade power: limit what upgrades can change (for example forbid changing token balances logic without a longer delay), use modular designs where only parameters or non-critical modules are upgradeable, and consider sunsetting upgradeability once the code is mature.
  • Monitoring: alerts on upgrade events, admin role changes, implementation slot changes, and timelock queue entries (see 17_reliability-and-monitoring.org).

6. Migrations

  • Contract migrations (new deployment): users move funds voluntarily (with incentives), or an owner-driven migration with user consent and a deadline; handle approvals (users must re-approve), integrations, oracles, and indexers; keep the old contract alive in a wind-down mode.
  • State migrations during upgrades: a one-time migration function (reinitializer) with bounded gas, or lazy migration on first touch; test with realistic state at scale.
  • Token and liquidity migrations: coordinate with exchanges, bridges, and wallets; use snapshot-based claims for large populations (Merkle claims).
  • Chain migrations: moving to another chain or L2 involves bridging assets, redeploying, and retiring the old deployment; communicate timelines and risks.
  • Deprecation: define end-of-life, final withdrawal windows, and what happens to unclaimed funds.

7. Incident-driven changes

  • Prepare runbooks for pause, upgrade, key rotation, and communication; practice them.
  • Hotfix path: a fast, tightly controlled process (small reviewed patch, dedicated multisig, shortened timelock only if the governance allows and is disclosed), balanced against the risk of rushing code to production.
  • Post-incident: public post-mortem, regression tests, process changes (see 16_security-auditing.org).

8. Self-check

  1. Write the deployment checklist you would require before a mainnet launch of a vault protocol.
  2. Why must the implementation constructor call _disableInitializers(), and what attack does that prevent?
  3. Compare transparent and UUPS proxies: failure modes, costs, and who can upgrade.
  4. What does ERC-7201 solve compared with storage gaps, and what must still be reviewed in an upgrade?
  5. Design the governance of upgrades for a lending protocol: roles, delays, emergency powers, and transparency.
  6. A critical bug is found while an upgrade is queued in the timelock. What do you do?

9. Exercises

  • Warm-up: write a deployment script, run it on a local fork, and produce a manifest; verify the contract source on a testnet explorer.
  • Core: implement a UUPS proxy upgrade from V1 to V2 with a new storage variable; use an upgrade-safety plugin; write fork tests comparing state before and after.
  • Core: demonstrate a storage collision from reordering variables and fix it with append-only changes and namespaced storage.
  • Core: build a post-deployment verification script that reads roles, owners, parameters, and implementation slots and fails on any deviation from a specification file.
  • Stretch: deploy a timelock and multisig, queue an upgrade, monitor it with an alert, and execute after the delay; document the runbook.
  • Stretch: plan and rehearse a contract migration with a deadline, incentives, and a Merkle claim for remaining users.

What to remember

  • Deployment is an irreversible release: reproducible builds, scripted and rehearsed steps, verified sources, and post-deploy checks.
  • Upgradeability is a trust assumption; govern it with timelocks, multisigs, transparency, and narrow emergency powers.
  • Storage layout and initializer mistakes silently corrupt state; use standard patterns and tools.
  • Plan migrations, rollbacks, and hotfix procedures before launch.
  • Record the immutability decision and review triggers.
