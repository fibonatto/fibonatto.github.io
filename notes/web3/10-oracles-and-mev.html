Oracles and MEV

Oracles and MEV

0. Staff-level lens

Contracts cannot see the outside world, and public mempools let others see and reorder your transactions. Oracles and MEV are the two ways the environment attacks protocol assumptions: wrong or manipulated inputs, and adversarial ordering. At Staff and Principal scope you are expected to:

  • choose and configure oracle designs with a clear model of manipulation cost, staleness, failure modes, and governance;
  • design protocol mechanics (liquidations, auctions, swaps, oracle updates) that are robust to extractive ordering;
  • reason about the MEV supply chain (searchers, builders, relays, proposers) and its centralization and censorship risks;
  • decide when to use private order flow, batch auctions, or intents, and what they trust.

Companion files: 03_smart-contract-security.org, 06_transactions-and-gas.org, 14_protocol-design.org, 11_layer-2-and-cross-chain.org.

1. The oracle problem

  • Problem: a blockchain is a closed deterministic system; prices, events, randomness, and off-chain facts must be brought in by parties whose honesty cannot be verified by the chain itself. Any oracle is a trust assumption.
  • Oracle types:
    • Decentralized oracle networks (for example Chainlink data feeds): independent node operators fetch from data providers, aggregate off-chain, and post updates when a deviation threshold or a heartbeat interval is reached.
    • Pull-based oracles (for example Pyth): publishers sign price updates; consumers submit a fresh update in the same transaction that uses it (paying a fee), which gives low latency and puts update responsibility on the caller or the protocol.
    • AMM-derived oracles: time-weighted average prices (TWAP) from automated market makers (for example Uniswap v3 oracle observations); cost of manipulation depends on liquidity and window length.
    • First-party oracles: data providers run their own nodes (API3-style).
    • Optimistic oracles (for example UMA): assertions accepted unless disputed within a window; suited to non-price facts and event resolution.
    • Governance or committee oracles: a multisig or signer set reports values; simple, with explicit trust.
    • On-chain computed values: internal accounting rates (share price, exchange rates) used as prices for tokens like staking derivatives, with their own manipulation vectors.
  • What to ask of any oracle: who can update or censor it, how it aggregates, how quickly it reflects the market, what its failure modes are (stale, wrong, paused, delisted), and what its update incentives and costs are.

2. Oracle risks and defenses

  • Staleness: a feed that has not updated within its heartbeat during a quiet market is fine; one that has not updated for hours during volatility is dangerous. Check the last update timestamp and revert or degrade beyond a maximum age appropriate to the asset.
  • Invalid values: zero or negative answers, round id inconsistencies, and decimals that differ per feed (normalize explicitly).
  • Manipulation: spot prices from thin pools can be moved within one transaction (flash loans); TWAPs raise the cost but can be manipulated over a window if liquidity is low; consider the cost to move the price versus the profit extractable from the dependent protocol.
  • Deviation and circuit breakers: bound the allowed change between updates or versus a secondary source; pause sensitive actions (borrowing, liquidations) when sources disagree beyond a threshold, with a clear recovery process.
  • Multiple sources: use a primary with a fallback (for example an oracle plus a TWAP) or a median of several, understanding the correlation between them; fallback logic is code that attackers will probe.
  • Depegs and exotic assets: stablecoins and liquid staking tokens can trade away from their reference; price them through the actual market, with caps and risk parameters.
  • L2 sequencer risk: on rollups, if the sequencer is down, feeds may be stale while users cannot transact; sequencer uptime feeds and grace periods after restart prevent unfair liquidations.
  • Oracle extractable value (OEV): the update transaction itself is a valuable ordering event (liquidations depend on it); some designs auction the right to update.
  • Governance and configuration: feed addresses, heartbeats, and decimals are configuration; changing or mis-setting them is a common failure. Treat feed changes as privileged, timelocked actions.
  • Cost: push oracles are paid by the oracle network or sponsors; pull oracles charge per update; model costs at your volume.
// Reading a Chainlink-style price feed defensively.
import {AggregatorV3Interface} from "@chainlink/contracts/src/v0.8/shared/interfaces/AggregatorV3Interface.sol";

contract PriceReader {
    AggregatorV3Interface public immutable feed;
    uint256 public immutable maxStaleness;       // seconds, chosen per asset and feed heartbeat

    error InvalidPrice();
    error StalePrice();

    constructor(address feed_, uint256 maxStaleness_) {
        feed = AggregatorV3Interface(feed_);
        maxStaleness = maxStaleness_;
    }

    function price() public view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = feed.latestRoundData();
        if (answer <= 0) revert InvalidPrice();
        if (block.timestamp - updatedAt > maxStaleness) revert StalePrice();
        return uint256(answer);                  // normalize using feed.decimals() before use
    }
}

3. What MEV is

  • Maximal (originally miner, now maximal) extractable value: the profit available to whoever controls transaction ordering, inclusion, or censorship in a block, beyond fees. It exists because transactions are public before inclusion and because many protocols create profitable ordering opportunities.
  • Common strategies:
    • Arbitrage: equalize prices across venues; mostly benign and price-correcting.
    • Liquidations: repay unhealthy loans for a bonus; necessary for solvency, competitive, and sometimes harmful if the bonus is excessive or oracle updates are exploited.
    • Sandwich attacks: buy before a victim's swap and sell after, extracting slippage from the victim.
    • Front-running and back-running: copying or following a profitable transaction (token launches, NFT mints, governance, oracle updates).
    • Just-in-time liquidity: provide liquidity for a single block to capture fees.
    • Time-bandit and reorg attacks: reorganizing recent blocks to capture past MEV (a risk where finality is weak).
  • Who pays: users via worse execution; protocols via arbitrage leakage; the network via priority gas auctions and congestion; and the system via centralization of block building.
  • Not all MEV is bad: arbitrage and liquidation keep markets and lending protocols healthy; the engineering aim is to make extraction less harmful and its proceeds more fairly distributed.

4. The MEV supply chain

  • Searchers find opportunities and submit bundles with bids. Builders assemble full blocks, maximizing value, and bid to proposers. Relays escrow blocks between builders and proposers (trust-minimizing intermediaries in the current market). Proposers (validators) choose the highest-paying block header without seeing contents.
  • MEV-Boost implements this proposer-builder separation outside the protocol; most Ethereum blocks have been produced through it. Consequences: block building is concentrated in a few builders; relays are trusted for fair play and censorship policies; builders can censor (for example sanctioned addresses).
  • Enshrined PBS (ePBS): planned for the Glamsterdam upgrade (EIP-7732) to move this separation into the protocol and reduce reliance on relays. Inclusion lists and other censorship-resistance proposals aim to let proposers force inclusion of some transactions. Check the current status of these changes.
  • On L2s: ordering is controlled by the sequencer (often one operator), with first-come-first-served or priority-fee policies; shared and decentralized sequencers are in development. MEV on L2s depends on the sequencer's rules and may be extracted by the operator.
  • Economics: MEV revenue reaches validators and thus stakers, adding to rewards; it also pressures decentralization because sophisticated operators earn more.

5. Protecting users and protocols

  • Application-level defenses:
    • Slippage limits and deadlines on swaps bound the loss from a sandwich; they do not remove it. Set limits tightly by default and warn on high-slippage settings.
    • Private transaction submission (Flashbots Protect, MEV Blocker, builders' private endpoints) hides transactions from the public mempool and reduces sandwiching; it introduces trust in the relay or builder and may slow inclusion.
    • Batch auctions and intents: execute many orders at a uniform clearing price within a batch (for example CoW Protocol), or let users sign intents that solvers fulfil competitively (UniswapX, Across-style intents); ordering within the batch no longer matters and solvers compete to improve prices.
    • Commit-reveal for actions where hidden information matters (auctions, mints, votes).
    • Design out profitable ordering: avoid mechanisms where the first caller wins a fixed bonus (use auctions for liquidations with decaying discounts), avoid predictable on-chain randomness, and avoid state that can be profitably moved and restored within a block.
    • Oracle design: update oracles in ways that do not create a guaranteed profit for the updater, or auction the update right (OEV capture).
    • Fee design: priority fee auctions create congestion externalities; consider base-fee-only designs for time-insensitive actions.
  • Protocol-level research: encrypted mempools, threshold-decryption ordering, fair-ordering protocols, MEV burn and smoothing, and application-specific sequencing; none is a complete solution today.
  • User-side practices: use private RPC endpoints for swaps and large trades, set slippage and deadlines, split trades, and prefer venues with MEV protection; wallets and frontends should default to protective routes.

6. Integrating oracles and MEV into protocol design

  • Lending: oracle choice determines liquidation fairness; use TWAP or robust feeds with deviation checks; design the liquidation bonus and close factor to attract liquidators without enabling profitable manipulation; plan for oracle failure (pause or conservative mode).
  • AMMs: exposure to sandwiches depends on pool depth and price impact; offer slippage controls and protective routing; fee tiers, concentrated liquidity, and hooks change the MEV surface.
  • Vaults and strategies: harvest and rebalance transactions are MEV targets; use private submission, randomization, and bounded slippage; avoid revealing predictable schedules.
  • Governance: proposals executed after timelocks can be front-run by informed actors; consider this in treasury operations.
  • Cross-chain: message relays and settlements can be reordered or delayed; design for out-of-order delivery and slippage across chains (see 11_layer-2-and-cross-chain.org).
  • Simulation: replay historical blocks on a fork with adversarial searchers; compute the maximum extractable value of your design under stress using agent-based or scripted attacks.

7. Self-check

  1. A protocol uses a Uniswap v3 TWAP over 30 minutes as a price for collateral on a pool with modest liquidity. Estimate how an attacker might manipulate it and what parameters change the cost.
  2. List the checks a consumer of a push-based price feed should perform, and which extra ones apply on an L2.
  3. Describe how a sandwich attack works with a constant-product pool and how slippage limits bound it.
  4. Compare private order flow, batch auctions, and intents: what does each trust and what does each cost?
  5. Why does the MEV supply chain tend to concentrate, and what are the censorship consequences?
  6. Design a liquidation mechanism that minimizes harmful MEV while ensuring timely liquidations.

8. Exercises

  • Warm-up: write the defensive price-reader above with tests for stale, zero, negative, and normal values using a mock feed.
  • Core: implement a TWAP oracle against an AMM pool in a local test and demonstrate (in a test environment) how liquidity and window length affect manipulation cost.
  • Core: simulate a sandwich attack on a constant-product pool in a script; compute the victim's loss as a function of slippage tolerance and pool depth.
  • Core: build a liquidation module with a decaying-discount auction and compare it with a fixed-bonus design in a simulation with several searchers.
  • Stretch: build a pull-oracle consumer that updates and uses a price in one transaction with a maximum age and a fallback.
  • Stretch: write a report on the MEV exposure of a real protocol's key operations (swap, liquidation, harvest, oracle update) and propose mitigations.

What to remember

  • Every oracle is a trust and manipulation assumption; check freshness, validity, deviation, and sequencer status.
  • TWAPs raise manipulation cost but depend on liquidity and window; combine sources with circuit breakers.
  • MEV is a property of public ordering; design mechanisms that do not reward first-come ordering games.
  • Private flow, batch auctions, and intents shift trust; choose knowingly.
  • Simulate adversarial ordering against your design before launch.
